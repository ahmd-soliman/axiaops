## 1. Scope and non-goals

### 1.1 In scope — what the Terraform provisions

The Terraform in `infra/terraform/` is responsible for **every AWS resource that exists in the production account `123456789012` in region `eu-central-1`**, with one bootstrap-only exception (§4). Concretely:

1. **Networking**
   - One VPC (10.0.0.0/16), two public subnets across two AZs, one Internet Gateway, one default route table.
   - One VPC connector for App Runner (egress to RDS).
   - Security groups: one for App Runner (egress-only to RDS), one for RDS (ingress 5432 from the App Runner SG, deny-all else).
   - **No NAT Gateway.** ~€33/mo would singlehandedly blow the €24-34 envelope. See §5.

2. **Data**
   - One RDS PostgreSQL 16 instance, `db.t4g.micro`, Single-AZ, 20 GB gp3, 7-day automated backups.
   - One DB subnet group spanning both public subnets (RDS instance itself is `publicly_accessible = false` — public subnet placement is for the routing-table cost trick, not exposure).
   - One DB parameter group with `rds.force_ssl = 1`.
   - Two database roles: `axiaops_owner` (migrations owner) and `axiaops` (RLS app user). See §6 for the provisioning approach.

3. **Compute**
   - Three ECR repositories: `axiaops-api`, `axiaops-ingestion`, `axiaops-migrate`. (Dashboard does **not** get one — see §9.)
   - Two App Runner services: `axiaops-api` (port 8080) and `axiaops-ingestion` (port 8081). Both wired to the VPC connector, both with auto-deployment **disabled** (CI pushes images and explicitly calls `apprunner update-service` — see §7).
   - One App Runner instance role per service, scoped to the secrets each consumes (§10).
   - One ECS task definition for `axiaops-migrate` (run as a one-off Fargate task per release — §13).

4. **Secrets**
   - SSM Parameter Store SecureString parameters for every secret the App Runner services consume. See §8 for the SM-vs-SSM justification.
   - The `axiaops_owner` password is generated by Terraform (`random_password`) and stored as a SecureString; the rotated value never leaves AWS. The `axiaops` app-user password follows the same pattern.

5. **Edge**
   - One S3 bucket holding the dashboard SPA bundle.
   - One CloudFront distribution fronting the S3 bucket, with an origin behaviour that proxies `/api/*` and `/v1/*` to the App Runner api service.
   - One ACM cert in `us-east-1` (CloudFront's required region) for `app.axiaops.io`.
   - Route 53 hosted zone for `axiaops.io`, with A/AAAA records for `app.axiaops.io` → CloudFront.

6. **Observability**
   - One CloudWatch log group per App Runner service, 7-day retention.
   - **No** CloudWatch alarms, **no** Prometheus scraping, **no** Grafana — all out of scope today (§11).

7. **IAM seam for CI**
   - One IAM role `gitlab-ci-axiaops-deploy` with a trust policy permitting OIDC federation from `gitlab.com` for the `axiaops/axiaops` project.
   - The role is scoped to: push to the three ECR repos, run a Fargate task against the `axiaops-migrate` task definition, call `apprunner:UpdateService` on the two specific service ARNs, invalidate the CloudFront distribution, sync to the dashboard S3 bucket.
   - Replaces the current `gitlab-ci-axiaops` IAM **user** with long-lived access keys (`docs/CI_CD_SECRETS_SETUP.md` step 1.1) — see §10.

### 1.2 Explicitly out of scope — what the Terraform does NOT provision

- **GitLab CI configuration.** `.gitlab-ci.yml` stays as it is, with deploy job variables (assumed AWS role ARN, etc.) updated to point at the new role. The contract is one-way: TF outputs the role ARN; CI consumes it via a project variable.
- **Self-hosted v1 customer infrastructure.** Tasks.md §2.7.3 (`docker-compose only, defer Helm`) and ADR-0001 establish that customers self-host. AxiaOps prod is the same code path running for AxiaOps's own internal-use instance and design partners we host — not the multi-tenant SaaS data plane.
- **GitLab project-side secrets** (the `AWS_ACCESS_KEY_ID` we're decommissioning, the `LICENSE_SIGNING_KEY` File-type variable from `docs/license-issuance.md`). These remain in GitLab project settings and are NOT mirrored into Terraform — secrets that live outside AWS stay outside AWS.
- **Customer data lake / cross-account role infrastructure.** Customer AWS accounts grant AxiaOps a read role (`docs/cross-account-roles-design.md`); the trust relationship lives in the **customer's** account, not ours. We only TF the role-ARN allowlist if/when that becomes a thing.
- **WAF in front of CloudFront or App Runner.** Deferred per §14 — low traffic, cost-additive, no compliance obligation pre-SOC 2.
- **Site-to-site VPN, Direct Connect, or bastion host.** All operator access to AWS is via SSO (humans) or OIDC-federated IAM roles (CI). RDS shell access is via `ec2-instance-connect` style ephemeral session or — when truly needed — by spawning a one-off Fargate task with a temporary `psql` ENTRYPOINT. No bastion to harden.
- **EventBridge cron for scheduled scans.** Tasks.md §2.16 lists this, but the in-process ticker in `services/api` already handles scheduled scans on a per-account `scan_interval_hours` field. The EventBridge approach is deferred until a real multi-process or zero-scale-to-zero requirement emerges.
- **Multi-region**, **read replicas**, **Multi-AZ RDS**, **App Runner private services for ingestion**, **ElastiCache** — all deferred (§14).

### 2.2 Request flows

**Browser → dashboard load.**
1. Browser hits `https://app.axiaops.io/`. Route 53 resolves to the CloudFront distribution.
2. CloudFront serves the `index.html` + `/assets/*` SPA bundle from the S3 origin.
3. The SPA boots, reads `window.__ENV__` from `/runtime-env.js`. In production this file is a static asset baked into the S3 bundle by the dashboard build job (no runtime `inject-env.sh` because there's no nginx container; see §9 for why this is a real change from the compose shape).

**Browser → api call.**
1. SPA fires `fetch('/api/v1/zombies', { credentials: 'include' })`.
2. CloudFront sees the `/api/*` prefix, routes to the App Runner api origin (Origin 2).
3. CloudFront strips the `/api` prefix via a Function or Cache Behaviour path rewrite, sets `X-Forwarded-Proto: https`.
4. App Runner terminates HTTPS at its edge and forwards plaintext to the api container on port 8080.
5. The api uses `X-Forwarded-Proto` to set the `Secure` flag on the session cookie correctly (`services/api/internal/auth/cookie.go` — same logic as the nginx-fronted compose path documented in `CLAUDE.md` → "Deployment topology").
6. api runs the request inside an RLS-scoped Postgres transaction over the VPC connector → RDS.

**api → ingestion call.**
1. api issues `POST /scan` to the ingestion service URL.
2. **Path A — direct App Runner public URL** (the App Runner public service URL `axiaops-ingestion-<rand>.eu-central-1.awsapprunner.com`): the request leaves App Runner api, hits AWS's public network, comes back into App Runner ingestion.
3. **Path B — App Runner private service** (the ingestion service exposed inside the VPC connector, not on the public internet): the request stays inside the VPC.

   **Decision: Path A for v1, Path B deferred.** Path B requires marking ingestion as a "Private service" which adds setup complexity (App Runner private services are GA but the IAM and connector wiring is fiddly) without a security win — the call is HMAC-authenticated end-to-end via C-1 (`docs/c1-hmac-plan.md`), so plaintext bodies on the public hop are non-confidential and signature-verified. The defence-in-depth argument for private services lands after we ship C-1 and have logs to prove ingestion's public surface gets zero unsigned hits; revisit then.

4. ingestion verifies the HMAC, runs the scan against the customer's AWS account using the ingestion App Runner instance role (`AxiaOpsReadOnly`), writes results back through the VPC connector to RDS.

### 2.3 Why these shapes

- **App Runner over ECS Fargate or EKS.** App Runner scales to zero, charges only for active instance-hours, and removes ALB + listener + target-group plumbing. The 2025 pricing is ~€0.007/instance-hour at the smallest config; an api service that handles bursty traffic from one operator's browser plus a once-per-24h scan trigger costs <€5/mo. ECS Fargate would be €15-25/mo minimum because it doesn't scale to zero and the ALB adds €18/mo. EKS is nonsense at this scale.
- **Single region (eu-central-1).** EU data residency for the customers we target. Multi-region would 2× the data layer cost and there's no SLA story that needs it pre-Phase-3.
- **Single AZ for RDS.** Multi-AZ doubles the RDS bill (~€24/mo instead of €12/mo) for the benefit of <2-minute failover during a Frankfurt AZ outage — a real but accept-the-risk trade for AxiaOps's own internal-use prod. Customers who care self-host (ADR-0001).
- **Public subnets only, no NAT GW.** ~€33/mo for the NAT GW + €0.045/GB processed would land us €60+/mo. App Runner with a VPC connector in public subnets reaches AWS APIs and the internet via the subnet's IGW route. Reachability story: RDS is `publicly_accessible = false` so an SG-attached SG attack surface is the only ingress — see §5 for the security analysis. **This is the load-bearing cost decision.**
- **SSM Parameter Store SecureString over Secrets Manager.** Secrets Manager is €0.40/secret/mo × 6 secrets = €2.40/mo. SSM standard SecureString parameters are free. The only Secrets Manager feature we'd use (managed rotation for RDS passwords) requires a Lambda rotator we don't have today. See §8 for the full justification.
- **CloudFront + S3 over App Runner-served dashboard.** A static SPA on S3 + CloudFront is €0.50-€2/mo for AxiaOps-sized traffic. The same dashboard served by an App Runner container would be €5-€10/mo plus a redundant nginx container. The compose-mode nginx-+-`inject-env.sh` shape exists because compose has no equivalent to CloudFront; production doesn't. See §9.

### 3.2 Per-module responsibilities

| Module | Owns | Reads from | Surfaced outputs |
|---|---|---|---|
| `network` | VPC, subnets, IGW, route table, App Runner & RDS security groups, VPC connector | nothing (root) | `vpc_id`, `public_subnet_ids`, `apprunner_sg_id`, `rds_sg_id`, `vpc_connector_arn` |
| `data` | RDS instance, subnet group, parameter group, db role provisioning | `network.public_subnet_ids`, `network.rds_sg_id`, `secrets.owner_password_arn` | `rds_endpoint`, `rds_port`, `database_url_ssm_arn`, `migration_database_url_ssm_arn` |
| `secrets` | All SSM SecureString parameters; `random_password` resources for db roles | `data.rds_endpoint` (to compose connection strings) | individual SSM parameter ARNs |
| `compute` | ECR repos, App Runner services, ECS task definition for migrate, App Runner instance roles | `network.vpc_connector_arn`, `secrets.*_ssm_arn`, `iam.apprunner_instance_role_arn` | App Runner service ARNs, ECR repo URLs |
| `edge` | S3 bucket + bucket policy, CloudFront distribution + OAI, ACM cert (us-east-1), Route 53 zone + records | `compute.apprunner_api_service_url` (for CloudFront origin) | dashboard URL, S3 bucket name, CloudFront distribution ID |
| `iam` | GitLab CI OIDC role, App Runner instance roles, ECS migrate task role | `compute.ecr_repo_arns`, `compute.apprunner_service_arns`, `edge.cloudfront_distribution_arn`, `edge.s3_bucket_arn` | CI deploy role ARN, App Runner instance role ARN |
| `observability` | CloudWatch log groups | App Runner service names (to predict log group names) | log group ARNs |

The `iam` module reads from almost every other module — that's a feature, not a bug. IAM policies must be **resource-scoped** (least privilege), and the only way to scope a `apprunner:UpdateService` permission to "only the two services we created" is to know those services' ARNs. The reverse dependency would mean blanket `Resource: "*"` policies, which we are explicitly avoiding.

### 3.3 Why this layout vs alternatives

**Alternative A — single flat root module.**

Pros: zero abstraction tax; one `terraform plan` shows everything; no module-version pinning to think about.

Cons: every var passed through one giant `variables.tf`; impossible to provision staging independently from production without copy-paste; hard to read in a code review (300+ resources in one file).

Rejected because the staging-environment story (constraint 8) is real even if staging isn't in the first apply. The module shape makes a future `environments/staging/main.tf` a 50-line file that calls the same modules with different vars.

**Alternative B — Terragrunt with DRY hierarchical includes.**

Pros: industry-standard for multi-env Terraform; eliminates the `environments/*/main.tf` copy-paste.

Cons: adds a binary dependency (operators install `terragrunt` in addition to `terraform`); adds a config layer (`terragrunt.hcl` files) on top of the existing TF abstraction; the value only materialises once you have 3+ environments. For staging + production, vanilla TF workspaces or the `environments/` directory pattern is sufficient.

Rejected for now. Revisit when we provision a third env (e.g. customer-shared single-tenant SaaS slot).

**Alternative C — Pulumi or CDK.**

Pros: real programming language; type-checked; better refactoring story.

Cons: zero AxiaOps prior art; community for AWS infra patterns is much smaller than HashiCorp's; locks us into a non-standard tool the next contractor probably doesn't know.

Rejected. HCL is the lingua franca for AWS infrastructure; the marginal pain of HCL is worth the marginal benefit of hireability.

**Decision: vanilla Terraform with the module + environments shape above.** Pluggable into Terragrunt later if multi-env count grows.

### 3.4 Terraform version + provider versions

- Terraform: 1.9.x, pinned in `.terraform-version` for `tfenv`. Choose a patch release; do not float to a major version.
- AWS provider: `~> 5.60` (so `5.60.x` through `5.99.x` is acceptable; `6.0.0` requires a deliberate bump and re-test). Latest AWS provider supports App Runner private services, VPC connectors, and CloudFront origin access controls — all of which we rely on.
- Random provider: `~> 3.6` for `random_password` (used for db role passwords).
- TLS provider: `~> 4.0` (only needed in `iam` for the GitLab OIDC thumbprint, which the provider can compute deterministically rather than us hardcoding it).

Pin via the standard `required_providers` block in each module's `providers.tf` (or in `versions.tf` if we want them split).

## 4. State backend

### 4.1 Shape — S3 + DynamoDB lock

Standard pattern. Per environment, the state lives at:

```
s3://axiaops-tf-state-123456789012/production/terraform.tfstate
s3://axiaops-tf-state-123456789012/staging/terraform.tfstate
```

With locking via DynamoDB table `axiaops-tf-state-lock` (key: `LockID`, on-demand billing).

The S3 bucket is:
- Versioning **enabled** (so a botched `terraform destroy` or local `rm` doesn't permanently corrupt state).
- Server-side encryption with the AWS-managed `aws/s3` KMS key (no custom KMS key — the marginal security gain doesn't pay for the €1/mo and the IAM complexity).
- Bucket policy denies all `s3:*` from anything not the Terraform-applying principal (the operator's SSO role + the GitLab CI role for plan-only previews — see §10).
- Public access fully blocked via S3 Block Public Access.

The DynamoDB table is:
- On-demand billing — at our `terraform apply` cadence (a few times a month), provisioned capacity would round to zero anyway.
- No backup. Losing the lock table loses **locking**, not state — and the lock TTL is short. Worst case: two operators apply simultaneously and the second one's plan fails on a stale `serial` field in the S3 state.

### 4.2 Bootstrap chicken-and-egg

Terraform can't manage the bucket that holds its own state — applying changes to the state backend mid-apply has no defined semantics.

**Solution: a small `infra/terraform/bootstrap/` module, applied exactly once with a local backend.**

The bootstrap module creates:
- The S3 bucket (with versioning, encryption, public-access-block).
- The DynamoDB lock table.
- An IAM role `axiaops-tf-state-readonly` that grants `s3:GetObject` + `s3:ListBucket` on the state bucket (used by the GitLab CI plan-only seam in §10).
- An S3 bucket policy that denies all access except the principals listed above.

**Bootstrap procedure** (operator runs this exactly once at AWS account inception):

```bash
cd infra/terraform/bootstrap
terraform init                       # uses local backend
terraform apply
# Capture the resulting state file and commit it.
git add terraform.tfstate
git commit -m "infra: terraform bootstrap state (one-time)"
git tag bootstrap-applied-2026-05-18
```

The committed `terraform.tfstate` is **fine in git** for two reasons:
1. It contains no secrets — the bootstrap module deliberately provisions only the state-bucket and lock-table resources, neither of which carry sensitive data.
2. We will never re-run `terraform apply` against the bootstrap module; the committed state exists only as a "we did this, this is what got created" audit trail.

After bootstrap, the `environments/production/providers.tf` declares the S3 backend:

```hcl
terraform {
  backend "s3" {
    bucket         = "axiaops-tf-state-123456789012"
    key            = "production/terraform.tfstate"
    region         = "eu-central-1"
    dynamodb_table = "axiaops-tf-state-lock"
    encrypt        = true
  }
}
```

And on first `terraform init`, the operator runs `terraform init -migrate-state` once to push the empty-state baseline into S3.

**Alternative considered: AWS-account-bootstrap via CloudFormation.** A CFN stack that creates the state bucket and lock table, then handing off to Terraform. Rejected because it introduces a second IaC tool for one bootstrap concern; the local-backend-one-time approach is the standard pattern and well-documented.

**Alternative considered: Terraform Cloud / HCP state backend.** Rejected because it's a paid SaaS dependency (~$15/operator/mo for the team plan), conflicts with the "everything in our AWS account" principle, and provides features (run pipelines, policy-as-code) we don't need at this scale.

**State-bucket destruction recovery.** S3 versioning protects against object overwrites and deletions, but not against bucket deletion (`aws s3 rb --force` removes the bucket and all versions). If the state bucket is accidentally deleted:

1. Recreate the bucket manually with the same name and the same lifecycle config (versioning, encryption, public-access-block).
2. Restore the bootstrap state from the committed `infra/terraform/bootstrap/terraform.tfstate` snapshot in git — that snapshot has the bucket resource, so re-applying the bootstrap module against the recreated bucket is a no-op import.
3. For the **production environment state** (which is NOT committed to git): you have lost it. There is no offline backup. Recovery is `terraform import` against every live AWS resource, walked manually — a multi-day exercise. Mitigate by enabling **S3 Object Lock** on the state bucket in compliance mode (prevents `s3 rb --force` from succeeding for the retention window) once we have a single production deploy; the bootstrap module deliberately doesn't enable Object Lock because that would prevent recovery from a botched bootstrap-module apply during initial setup.

If the DynamoDB lock table is deleted: no state lost, only locking. Recreate the table; next `terraform apply` runs unlocked, which is fine for a single operator. Document this in `docs/ops.md`.

### 4.3 State separation per env

The S3 key is the only separation: `production/terraform.tfstate` vs `staging/terraform.tfstate`. **No workspaces.** Terraform workspaces share a backend bucket, share IAM, and are easy to confuse (`terraform plan` in the wrong workspace is a real footgun). Separate `environments/production/` and `environments/staging/` directories with separate backend configs makes "which env am I touching" syntactically obvious.

Both environments target the same AWS account `123456789012` today. If staging eventually moves to its own AWS account (best practice but not required at our scale), the providers.tf in each environment changes its `assume_role` block; the module code stays identical.

## 5. Networking

### 5.1 VPC + subnet plan

```
VPC                10.0.0.0/16
Public subnet A    10.0.1.0/24   (eu-central-1a)
Public subnet B    10.0.2.0/24   (eu-central-1b)
Internet Gateway   one
Route table        default — 0.0.0.0/0 → IGW
```

Two AZs because **RDS DB subnet groups require at least two subnets in different AZs**, even for Single-AZ RDS. (RDS uses the second subnet for Multi-AZ promotion if you ever flip the switch; for Single-AZ it's a no-op slot.) Both subnets are public — i.e. they have a route to the IGW — but the resources placed inside them (RDS, App Runner VPC connector ENIs) are configured to not be publicly addressable.

No private subnets, no NAT Gateway. **This is the load-bearing cost decision.** A NAT Gateway at €0.045/hr + €0.045/GB processed lands at €33/mo idle plus traffic — for a workload whose entire cost target is €24-34/mo, this is half the budget for zero security benefit at our scale.

### 5.2 The "public subnet, private resource" pattern

This shape needs careful security analysis because it superficially smells wrong.

**The RDS instance** has `publicly_accessible = false`. Even though it's in a public subnet (so its route table reaches the IGW), AWS will not assign it a public IP. The only way to reach it is:
- From inside the VPC (the App Runner VPC connector ENIs, which share the subnet).
- Via a peering connection or transit gateway (we have none).
- Via VPN or Direct Connect (we have none).

The RDS security group ingress rule is `tcp/5432 from sg-<apprunner_sg_id>`. **No CIDR-based ingress.** Even if someone managed to spin up an EC2 instance in our VPC, they would need to attach the App Runner SG (or change the RDS SG) to reach the DB. Both are TF-managed and audit-logged.

**The primary blast-radius limit is `publicly_accessible = false`, not the SG.** Even if an operator fat-fingers the RDS SG to allow `0.0.0.0/0:5432`, AWS will still not route inbound internet traffic to the RDS instance because no public IP has been assigned. The SG is defence-in-depth on top of `publicly_accessible = false`; the latter is the actual gate. Both layers should stay; document the ordering so a future change to either one is reviewed knowing which is load-bearing.

**The App Runner VPC connector** is what gives the App Runner services VPC reachability. The connector creates ENIs in our subnets with the App Runner SG attached. App Runner services that bind to the connector route their **egress to the VPC** via these ENIs. Egress to the public internet from the connector goes via the public-subnet IGW route (the standard "internet egress for public subnets" path), which is where ingestion's calls to `ce.eu-central-1.amazonaws.com`, `monitoring.eu-central-1.amazonaws.com`, etc. land.

The App Runner SG egress rules:
- `tcp/5432 → sg-<rds_sg_id>` (RDS)
- `tcp/443 → 0.0.0.0/0` (AWS API + outside-world HTTPS)
- `tcp/80 → 0.0.0.0/0` (rare HTTP fetches — OIDC discovery for license validation pre-issuance was previously cited as a case but is no longer relevant; defensible to drop, kept for now as defensive cushion)

No `tcp/* in` from anywhere — App Runner services receive inbound traffic via the App Runner managed HTTPS edge, not via the VPC. The connector is **egress only**.

### 5.3 Security group dependency graph

```
RDS SG  ◄──── ingress 5432 ──── App Runner SG
                                    │
                                    ├── egress 5432 → RDS SG
                                    ├── egress 443  → 0.0.0.0/0
                                    └── egress 80   → 0.0.0.0/0
```

Both SGs are managed by the `network` module. The App Runner instance services reference the SG by ARN via the VPC connector's `security_groups` argument — App Runner doesn't take SGs directly, it takes a connector, which carries the SGs.

### 5.4 Considered and rejected: VPC endpoints

VPC endpoints for S3, ECR, Secrets Manager, etc. would keep traffic on the AWS internal network instead of egressing through the IGW. Each endpoint is €7-€10/mo. At our traffic volume the data-transfer savings don't recover the per-endpoint cost; the security benefit (traffic doesn't cross the public internet) is real but redundant — all the AWS API calls happen over HTTPS to AWS-controlled endpoints. Revisit at €100+/mo data-transfer bills.

### 5.5 Considered and rejected: Private DNS / Route 53 Resolver

The `INTERNAL_DNS` env var documented in `CLAUDE.md` → "Deployment topology" for self-hosted IdP split-horizon DNS is **a customer-self-hosted concern, not an App Runner concern**. App Runner services use AWS's resolver by default and don't need split-horizon DNS — production AxiaOps uses a hosted IdP (Auth0, Keycloak Cloud, etc.) reached via public DNS. The `dns:` block in `deploy/*.yml` does not port to App Runner.

### 6.2 Provisioning the two DB roles

The `axiaops_owner` user is the RDS master user — RDS creates it at instance launch. The `axiaops` (RLS app user) is **not** an RDS-managed user; we need to create it ourselves with the right grants.

**Option A — `null_resource` + `local-exec psql`.**

```hcl
resource "null_resource" "app_user" {
  depends_on = [aws_db_instance.main]
  triggers   = { rds_endpoint = aws_db_instance.main.endpoint }
  provisioner "local-exec" {
    command = <<-EOT
      PGPASSWORD='${var.owner_password}' psql \
        -h ${aws_db_instance.main.address} \
        -U axiaops_owner \
        -d axiaops \
        -c "CREATE ROLE axiaops LOGIN PASSWORD '${var.app_password}';"
    EOT
  }
}
```

Pros: zero extra providers.
Cons: requires `psql` on the operator's machine; requires the operator's machine to reach RDS at apply time (which it can't, because RDS isn't publicly accessible — operator would need a VPN, bastion, or session-manager tunnel). Awful UX.

Rejected.

**Option B — `cyrilgdn/postgresql` Terraform provider.**

```hcl
provider "postgresql" {
  host     = aws_db_instance.main.address
  port     = aws_db_instance.main.port
  database = "axiaops"
  username = "axiaops_owner"
  password = var.owner_password
  sslmode  = "require"
}

resource "postgresql_role" "app_user" {
  name     = "axiaops"
  login    = true
  password = var.app_password
}

resource "postgresql_grant" "app_user_schema" {
  database    = "axiaops"
  role        = postgresql_role.app_user.name
  schema      = "axiaops"
  object_type = "table"
  privileges  = ["SELECT", "INSERT", "UPDATE", "DELETE"]
}
```

Pros: declarative.
Cons: same network-reachability problem — the provider connects from the operator's machine to RDS, which is not publicly accessible.

Rejected for the same reason.

**Option C — Fold role-creation into the migrate job.**

The `services/migrate/main.go` binary already runs all `001..NNN_*.up.sql` migrations against `MIGRATION_DATABASE_URL`. We add a new migration (e.g. `000_create_app_user.up.sql`) that does:

```sql
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'axiaops') THEN
    CREATE ROLE axiaops LOGIN PASSWORD :'app_password';
  END IF;
END
$$;
GRANT USAGE ON SCHEMA axiaops TO axiaops;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA axiaops TO axiaops;
ALTER DEFAULT PRIVILEGES IN SCHEMA axiaops FOR ROLE axiaops_owner GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO axiaops;
```

The migrate binary reads `APP_USER_PASSWORD` from its environment and passes it to `psql` via a parameter. The migrate ECS task definition pulls `APP_USER_PASSWORD` from SSM. **This is the only path that runs from inside the VPC, where the RDS instance is reachable.**

Pros: works without a bastion; uses our existing migration plumbing; idempotent.
Cons: the migrate binary now does two things (migrate schema + bootstrap app user). The `axiaops` user has to exist before the first `terraform apply` of the api/ingestion services completes, so apply order matters (§13).

**Recommendation: Option C.** Implementation note: the migration that creates the `axiaops` role is special — it runs once at instance birth. Subsequent runs are no-ops via the `IF NOT EXISTS` guard. Rotation of the `axiaops` password is a separate operational concern (§13) and does not go through this migration.

### 6.3 Connection string composition

Both `DATABASE_URL` (app user) and `MIGRATION_DATABASE_URL` (owner) are SSM parameters whose values Terraform composes from the RDS endpoint, port, and stored passwords:

```
DATABASE_URL          = postgres://axiaops:<app_pw>@<rds_endpoint>:5432/axiaops?sslmode=require
MIGRATION_DATABASE_URL = postgres://axiaops_owner:<owner_pw>@<rds_endpoint>:5432/axiaops?sslmode=require
```

`?sslmode=require` matches the `rds.force_ssl = 1` server-side enforcement. The owner connection string is **not** present in the runtime App Runner services' environment — only the migrate ECS task pulls it. See §7.4.

### 6.4 Backups and restore drill

RDS automated backups run nightly during `02:00-03:00 UTC` with 7-day retention. Manual snapshots can be triggered via `aws rds create-db-snapshot` for pre-release checkpoints; these don't expire.

**Restore drill** — must be rehearsed before first paying customer:

1. `aws rds create-db-snapshot --db-instance-identifier axiaops-prod --db-snapshot-identifier drill-$(date +%Y%m%d)`.
2. `aws rds restore-db-instance-from-db-snapshot --db-instance-identifier axiaops-restore-drill --db-snapshot-identifier drill-...` — restore to a new instance.
3. Point a one-off App Runner service revision at the restored instance via a hand-edited `DATABASE_URL` (do **not** run TF for this).
4. Verify the dashboard loads, scans run, recent zombies are present.
5. `aws rds delete-db-instance --db-instance-identifier axiaops-restore-drill --skip-final-snapshot`.

Drill cadence: quarterly. Document the run in `docs/ops.md` (to be created in a follow-up MR — this design doc does not create that file).


Notes on each block:

- **`source_configuration`** points at ECR; the `latest` tag is what App Runner pulls on the next deploy. The CI deploy job pushes a `:${IMAGE_TAG}` tag (immutable, branch-slug + short SHA), retags as `:latest`, and calls `apprunner update-service` with the SHA-tagged identifier — this matches `.gitlab-ci.yml:1013-1015`. Terraform's `image_identifier` is the **default** image; deploys override it via the CLI call.
- **`runtime_environment_variables`** = non-secret config; visible in App Runner console.
- **`runtime_environment_secrets`** = SSM parameter ARNs; App Runner fetches the value at task start and injects it as the named env var. **App Runner does not support hot-rotation of these secrets** — a change to the SSM value requires an `apprunner update-service` to take effect. Documented in §13.
- **`cpu = "0.25 vCPU"`, `memory = "0.5 GB"`** — the smallest billable config. For AxiaOps internal-use prod load, this is overkill on memory (Go services with this codebase footprint sit at ~80MB) and adequate on CPU (the api is mostly waiting on Postgres). Going below 0.25 vCPU is not an App Runner option.
- **Scaling posture: minimum 1 instance, not scale-to-zero.** The api sits behind CloudFront and must respond to operator browser traffic without a 5-15s cold start. The `auto_scaling_configuration_arn` attribute (not shown above) MUST reference a TF-managed `aws_apprunner_auto_scaling_configuration_version` with `min_size = 1, max_size = 2`. The cost estimate in §12.1 (api at €4.50/mo) assumes this minimum-1 posture — without it, App Runner defaults to "automatic" scale-to-zero and the api will cold-start visibly. Ingestion, in contrast, IS configured for scale-to-zero (`min_size = 0`) because it's only invoked on `POST /scan` and the operator-visible latency floor is the scan itself, not the binary's cold start.
- **`network_configuration.egress.vpc_connector_arn`** — wires the api into the VPC for RDS access. Without this the api would only have public-internet egress and couldn't reach RDS.
- **`ingress.is_publicly_accessible = true`** — required because the dashboard's CloudFront distribution routes to this service via its public URL. The alternative (private service) would require CloudFront to use a VPC origin, which App Runner doesn't directly support without an intermediate ALB.
- **`health_check_configuration.path = "/livez"`** — `/livez` is liveness (process is up); `/readyz` is readiness (process can serve traffic, DB reachable). App Runner's health check is per-instance liveness, so `/livez` is the right endpoint (`services/api/CLAUDE.md` Endpoints table). `/readyz` is for our future synthetic monitoring.

### 7.2 App Runner service: ingestion

Identical shape to api, with:
- `port = "8081"`.
- Different env-var set: no `PUBLIC_HOST`, no `CORS_ORIGIN`, no `INVITATION_TTL_DAYS`; same `DATABASE_URL`/`ENCRYPTION_KEY`/`AXIAOPS_LICENSE`; plus `INGESTION_SHARED_SECRET` and `INGESTION_SHARED_SECRET_NEXT` (see §8.3).

Plus a one-line policy granting `sts:AssumeRole` on `arn:aws:iam::*:role/AxiaOpsCrossAccountReader-*` to support the cross-account roles flow.
- Same `network_configuration` shape — VPC connector for RDS access, public ingress because the api needs to reach `POST /scan` and Path A (public hop, HMAC-protected) is the v1 decision.

### 7.3 Auto-deployment posture

App Runner's auto-deployment polls ECR every few minutes and redeploys when a tagged image changes. **We disable this** (`auto_deployments_enabled = false`) for three reasons:

1. **Predictability.** The existing CI pipeline already calls `apprunner update-service` explicitly (`.gitlab-ci.yml:1013-1023`). Auto-deploy would race the CI call.
2. **Tag immutability.** The CI pipeline pushes images with `${IMAGE_TAG} = ${CI_COMMIT_REF_SLUG}-${CI_COMMIT_SHORT_SHA}` (immutable per commit) AND retags as `:latest` (mutable). Auto-deploy keyed off `:latest` would redeploy on every tag change; we want deploys keyed off the SHA tag, with `:latest` as a "what's currently in prod" pointer.
3. **Manual gate parity.** Per the user-memory pin "All deploy:* jobs are manual gates", a human clicks the button. Auto-deploy bypasses the click.

The result: TF declares what App Runner runs at steady state (`:latest` from ECR), CI mutates that via SHA-tagged `apprunner update-service` calls. The TF state shows `latest`, the live service shows the SHA tag. **This drift is expected.** TF does NOT re-apply on `terraform plan` because the `image_identifier` change is what App Runner calls "in-progress" — TF sees the deployed revision via the data source, not the configured one, and the resource is considered up-to-date.

Wait — there's a subtle wrinkle here. Terraform's `aws_apprunner_service` resource does track `image_identifier` as a managed attribute. If TF declares `:latest` and CI pushes `:abc1234`, the next `terraform plan` will want to revert to `:latest`. Two options:

- **(a) `ignore_changes = [source_configuration[0].image_repository[0].image_identifier]`** in the lifecycle block. TF stops tracking that attribute. Drift is intentional.
- **(b) Make the image tag a `var.image_tag` passed at apply time** so the CI job that runs `apprunner update-service` also calls `terraform apply -var image_tag=abc1234`. More moving parts.

**Decision: (a).** The `lifecycle.ignore_changes` block is the canonical pattern for "this attribute is managed by CI, not TF." Drift is a feature.

The TF resource gets a comment documenting this explicitly, so the next operator running `terraform plan` six months later doesn't waste time tracing why TF reports no changes while the App Runner console shows `:main-abc5678`:

```hcl
resource "aws_apprunner_service" "api" {
  # ...
  lifecycle {
    # The image_identifier attribute is mutated by .gitlab-ci.yml's deploy
    # job (via aws apprunner update-service) on every deploy. TF state shows
    # ":latest" but the live service runs the most-recently-deployed SHA tag.
    # CI is the source of truth for what's deployed; check the App Runner
    # console or `aws apprunner describe-service` for the live image identifier.
    ignore_changes = [source_configuration[0].image_repository[0].image_identifier]
  }
}
```

### 7.4 The migrate service — ECS Fargate task, not App Runner

The migrate binary (`services/migrate/`) runs once per release: it applies any new `*.up.sql` migrations and exits. App Runner is for long-running HTTP services; a one-shot job is the wrong shape.

**Choice: ECS Fargate task definition, no service.** A task definition without a service is exactly the "run this container once" pattern. The CI deploy job calls `aws ecs run-task --task-definition axiaops-migrate --launch-type FARGATE --network-configuration ...` after pushing the migrate image to ECR but before calling `apprunner update-service` on the runtime services.

```hcl
resource "aws_ecs_task_definition" "migrate" {
  family                   = "axiaops-migrate"
  network_mode             = "awsvpc"
  requires_compatibilities = ["FARGATE"]
  cpu                      = "256"
  memory                   = "512"
  task_role_arn            = aws_iam_role.migrate_task.arn
  execution_role_arn       = aws_iam_role.migrate_execution.arn

  container_definitions = jsonencode([{
    name      = "migrate"
    image     = "${aws_ecr_repository.migrate.repository_url}:latest"
    essential = true
    secrets = [
      { name = "DATABASE_URL", valueFrom = aws_ssm_parameter.database_url.arn },
      { name = "MIGRATION_DATABASE_URL", valueFrom = aws_ssm_parameter.migration_database_url.arn },
      { name = "APP_USER_PASSWORD", valueFrom = aws_ssm_parameter.app_user_password.arn },
    ]
    logConfiguration = {
      logDriver = "awslogs"
      options = {
        "awslogs-group"         = aws_cloudwatch_log_group.migrate.name
        "awslogs-region"        = "eu-central-1"
        "awslogs-stream-prefix" = "migrate"
      }
    }
  }])
}
```

The task runs in a public subnet with `assignPublicIp=ENABLED` (so ECR + SSM API are reachable via the IGW route) and the App Runner SG attached (so it can reach RDS on port 5432). Single task, no service, no scheduler.

**The task needs an ECS cluster to run in** — and AWS does not provision a "default" cluster on its own. Accounts that have never used ECS (this one, since App Runner is the existing compute path) have no `default` cluster, so `aws ecs run-task --cluster default ...` returns `ClusterNotFoundException`. The compute module provisions a single-purpose cluster:

```hcl
resource "aws_ecs_cluster" "migrate" {
  name = "axiaops-migrate"
  setting {
    name  = "containerInsights"
    value = "disabled"   # +€6/cluster/mo if enabled; we don't need it for one-off tasks
  }
}
```

`aws ecs run-task` invocations in CI and in §13.1 step 9 pass `--cluster axiaops-migrate`, not `--cluster default`.

**Why not a Lambda?** Cold start ~2-5s for Go in Lambda. Migrations sometimes take 30-90s. Lambda's 15-minute timeout would technically suffice, but the artifact-size and cold-start dynamics make Fargate the cleaner shape — and we already have a Docker image for migrate.

**Why not a one-off App Runner deploy?** App Runner is designed for steady-state HTTP services; "deploy a one-shot container" isn't its model. ECS one-off tasks are.

```hcl
        action = { type = "expire" }
      },
      {
        rulePriority = 2
        description  = "Expire untagged after 7 days"
        selection = {
          tagStatus   = "untagged"
          countType   = "sinceImagePushed"
          countUnit   = "days"
          countNumber = 7
        }
        action = { type = "expire" }
      }
    ]
  })
}
```

Three repos (api, ingestion, migrate) with identical shape. The 30-tagged-image cap is a balance between rollback runway (~3-4 weeks of deploys at one deploy/day) and ECR storage cost (€0.10/GB/mo × ~500MB per multi-arch image = €0.05/image/mo × 30 = €1.50/mo per repo, or €4.50/mo across all three). Untagged-7d cleans up failed pushes.

## 8. Secrets

### 8.1 SSM Parameter Store SecureString — and why not Secrets Manager

The runtime needs six injected secrets, every one of which is consumed by an App Runner or ECS service:

| Name | Consumer | Notes |
|---|---|---|
| `ENCRYPTION_KEY` | api, ingestion | 32-byte hex, AES-256-GCM key for the `accounts.secret_encrypted` column. |
| `DATABASE_URL` | api, ingestion, migrate | app-user connection string. |
| `MIGRATION_DATABASE_URL` | migrate **only** | owner-user connection string. **Not** present on api/ingestion. |
| `INGESTION_SHARED_SECRET` | api (signer), ingestion (verifier) | HMAC key per C-1. 32-byte hex. |
| `INGESTION_SHARED_SECRET_NEXT` | ingestion verifier only | Rotation staging slot per C-1 §5. May be empty. |
| `AXIAOPS_LICENSE` | api, ingestion | RS256-signed JWT for the AxiaOps-internal-prod license. |

Plus two infra-internal secrets that runtime services never see:

| Name | Consumer | Notes |
|---|---|---|
| `axiaops_owner_password` | RDS provisioning, migrate task | RDS master user password. |
| `app_user_password` | migrate task | `axiaops` role password, written into the connection string. |

**Secrets Manager analysis.** AWS Secrets Manager costs **€0.40/secret/mo + €0.05/10k API calls**. Six SM secrets = €2.40/mo flat. Across staging + production = €4.80/mo. Not catastrophic, but real against a €24-34/mo budget — that's 7-14% of the budget on the secret-store choice alone. The SM features we'd pay for and not use:
- Managed rotation (Lambda-based). We have no rotators today and the secrets we'd want to rotate automatically (RDS passwords) require building a Lambda we won't write.
- Cross-region replication. Single-region.
- KMS-key-per-secret. Marginal IAM granularity benefit we don't need at this scale.
- Resource-based policies on the secret itself. SSM has the same via IAM identity policies.

**SSM Parameter Store SecureString analysis.** SSM **Standard** parameters are **free**. SSM **Advanced** parameters (>4KB, with policies) are €0.05/parameter/mo. Our secrets all fit in 4KB except potentially `AXIAOPS_LICENSE` — let's measure: a typical AxiaOps license JWT is ~600 bytes (header + claims + 4096-bit RS256 signature). Under 4KB. **All eight secrets fit in Standard, cost = €0.** App Runner natively supports SSM as a `runtime_environment_secrets` source (the same `valueFrom` shape SM uses).

What we lose vs SM:
- No "secret rotation" lifecycle metadata. We track rotation in our own runbook (§13).
- No cross-account access via resource policy. We don't need this.
- API throttling: SSM `GetParameters` has a per-account rate limit, and a redeploying App Runner service makes one call per secret on instance start. At our deploy cadence this is irrelevant.

**Decision: SSM Parameter Store SecureString for all eight secrets. Standard tier. No Advanced parameters.**

KMS: each SSM SecureString is encrypted with the AWS-managed `alias/aws/ssm` key. A customer-managed KMS key would cost €1/key/mo and give us auditable key-usage events; not worth it at v1. Revisit if SOC 2 type II calls for it.

### 8.2 Parameter naming convention

```
/axiaops/prod/api/ENCRYPTION_KEY
/axiaops/prod/api/DATABASE_URL
/axiaops/prod/api/AXIAOPS_LICENSE
/axiaops/prod/api/INGESTION_SHARED_SECRET
/axiaops/prod/ingestion/ENCRYPTION_KEY        # symlink-like — same value as api's, but separate ARN
/axiaops/prod/ingestion/DATABASE_URL
/axiaops/prod/ingestion/AXIAOPS_LICENSE
/axiaops/prod/ingestion/INGESTION_SHARED_SECRET
/axiaops/prod/ingestion/INGESTION_SHARED_SECRET_NEXT
/axiaops/prod/migrate/DATABASE_URL
/axiaops/prod/migrate/MIGRATION_DATABASE_URL
/axiaops/prod/migrate/APP_USER_PASSWORD
/axiaops/prod/infra/owner_password
/axiaops/prod/infra/app_user_password
```

The `/{env}/{consumer}/` hierarchy lets each service's IAM instance role allow only its own subtree:

```
arn:aws:ssm:eu-central-1:123456789012:parameter/axiaops/prod/api/*
arn:aws:ssm:eu-central-1:123456789012:parameter/axiaops/prod/ingestion/*
arn:aws:ssm:eu-central-1:123456789012:parameter/axiaops/prod/migrate/*
```

A compromised api container cannot read ingestion's parameters even though the values overlap (ENCRYPTION_KEY, AXIAOPS_LICENSE). The duplication of value-but-not-ARN is the lever that makes least-privilege ARN scoping work.

**Implementation note: the duplication is at the SSM layer.** Terraform writes the same `random_password`/JWT value to multiple parameter resources:

```hcl
resource "aws_ssm_parameter" "encryption_key_api" {
  name  = "/axiaops/prod/api/ENCRYPTION_KEY"
  type  = "SecureString"
  value = var.encryption_key  # supplied as TF_VAR_encryption_key at apply
}

resource "aws_ssm_parameter" "encryption_key_ingestion" {
  name  = "/axiaops/prod/ingestion/ENCRYPTION_KEY"
  type  = "SecureString"
  value = var.encryption_key
}
```

When the operator rotates the encryption key, both parameters update in the same apply, and a redeploy of both services picks them up atomically (well, near-atomically — see §13.2).

### 8.3 The C-1 two-secret rotation contract

`INGESTION_SHARED_SECRET` (primary) and `INGESTION_SHARED_SECRET_NEXT` (staging slot) are the C-1 plan's mechanism for zero-downtime HMAC rotation (`docs/c1-hmac-plan.md` §5). The TF implications:

- Three SSM parameters exist (not two): `/axiaops/prod/api/INGESTION_SHARED_SECRET` (what the signer uses), `/axiaops/prod/ingestion/INGESTION_SHARED_SECRET` (the verifier's primary slot), `/axiaops/prod/ingestion/INGESTION_SHARED_SECRET_NEXT` (the verifier's staging slot).
- During steady state, all three carry the **same** value (defensive duplicate per the C-1 design — `docs/c1-hmac-plan.md:539` recommends `_NEXT = X` even when no rotation is in flight, so the verifier code path is exercised continuously and `==""` isn't a load-bearing precondition).
- During rotation, the three parameters intentionally diverge for a window; see §13.2 for the sequenced playbook.

**Critical: the `secrets` module MUST expose three separate input variables, not one.**

```hcl
variable "api_ingestion_secret" {
  description = "What the api SIGNS with. Flipped to a new value in C-1 rotation Step 2."
  type        = string
  sensitive   = true
}

variable "ingestion_primary_secret" {
  description = "The ingestion verifier's primary slot. Promoted to the new value in C-1 rotation Step 3 only."
  type        = string
  sensitive   = true
}

variable "ingestion_next_secret" {
  description = "The ingestion verifier's staging slot. Staged with the new value in C-1 rotation Step 1, cleared in Step 3."
  type        = string
  sensitive   = true
  default     = ""
}
```

A single coupled variable would flip both api and ingestion-primary atomically in one apply, defeating the rotation sequence — the verifier's loaded process would still be running with the old primary while the SSM value has already flipped, and api's redeploy in Step 2 would land before ingestion is ready. The three-variable split keeps each apply's blast radius confined to one rotation step.

- The api consumes **only** `INGESTION_SHARED_SECRET` from its own subtree (signs with one secret).
- The ingestion service consumes both `INGESTION_SHARED_SECRET` and `INGESTION_SHARED_SECRET_NEXT` from its own subtree — the C-1 verifier walks them.

### 8.4 License JWT injection

`AXIAOPS_LICENSE` is the RS256-signed JWT from `docs/license-issuance.md`. Production injection:

1. Operator mints a license against the prod signing key:
   ```bash
   LICENSE_SIGNING_KEY_PATH=/tmp/signing.pem \
     go run ./services/api/cmd/license-issue \
       -customer-id=axiaops-internal-prod \
       -contract-id=internal-prod-$(date +%Y%m%d) \
       -days=365 \
       -max-organizations=10 \
       > /tmp/axiaops-prod.jwt
   ```
2. Operator writes the JWT into SSM (out-of-band, NOT via Terraform):
   ```bash
   aws ssm put-parameter \
     --name /axiaops/prod/api/AXIAOPS_LICENSE \
     --type SecureString \
     --value "$(cat /tmp/axiaops-prod.jwt)" \
     --overwrite
   aws ssm put-parameter \
     --name /axiaops/prod/ingestion/AXIAOPS_LICENSE \
     --type SecureString \
     --value "$(cat /tmp/axiaops-prod.jwt)" \
     --overwrite
   ```
3. Operator triggers a redeploy of both App Runner services (via the CI deploy button OR `aws apprunner start-deployment`).

**Terraform does NOT manage the JWT value.** The TF resource creates the parameter with a placeholder value (e.g. `lifecycle.ignore_changes = [value]`), the operator overwrites the value out-of-band. This matches the "license signing key never leaves the operator's laptop" posture from `docs/license-issuance.md`. If TF managed the JWT, the JWT would land in `terraform.tfstate` in S3 — which is itself encrypted and access-restricted, but adds an unnecessary access surface.

**Placeholder-vs-real check before compute lands.** The first-apply sequence (§13.1) puts step 4 (operator populates `AXIAOPS_LICENSE`) before step 7 (`module.compute` lands the App Runner services). If an operator follows the sequence wrong and skips step 4, the App Runner services start with the placeholder JWT — the license verifier rejects it at boot, scans 403 on `license_not_loaded`. Guard against this with a TF `precondition` on each App Runner service resource that asserts the live SSM value is not the placeholder sentinel:

```hcl
resource "aws_apprunner_service" "api" {
  # ... source/instance/network blocks ...
  lifecycle {
    precondition {
      condition     = data.aws_ssm_parameter.axiaops_license_live.value != var.license_placeholder_sentinel
      error_message = "AXIAOPS_LICENSE still holds the placeholder value. Run §13.1 step 4 (aws ssm put-parameter for the prod JWT) before applying module.compute."
    }
  }
}
```

This converts a silent post-deploy failure into a `terraform apply` error with a self-explaining message.

The plaintext JWT lives only in:

- The operator's laptop temp file (`shred -u` after upload).
- SSM (encrypted at rest by KMS).
- App Runner's task environment at runtime.

The 365-day rotation is a manual operator task on the calendar.

### 8.5 INGESTION_SHARED_SECRET — TF generates this

Unlike `AXIAOPS_LICENSE`, the HMAC secret is a `random_password` Terraform generates at apply time:

```hcl
resource "random_password" "ingestion_shared_secret" {
  length  = 64           # 64 hex chars = 32 bytes
  special = false        # hex character set
  upper   = false        # lowercase hex
  override_special = "" # belt-and-braces
}
```

Wait — that doesn't produce hex. Use `random_id` instead:

```hcl
resource "random_id" "ingestion_shared_secret" {
  byte_length = 32       # 32 bytes = 64 hex chars when expressed as hex
}

# value: random_id.ingestion_shared_secret.hex
```

**Wiring to the three §8.3 input variables.** At initial provisioning (and at every steady state) the single `random_id.ingestion_shared_secret.hex` value is passed as **all three** of the `secrets` module's input variables:

```hcl
module "secrets" {
  source = "../../modules/secrets"

  api_ingestion_secret     = random_id.ingestion_shared_secret.hex
  ingestion_primary_secret = random_id.ingestion_shared_secret.hex
  ingestion_next_secret    = random_id.ingestion_shared_secret.hex
  # ... other secrets
}
```

This is what makes the §8.3 "all three carry the same value" steady state literal in the code. During a C-1 rotation the operator hand-edits these three lines per the §13.2 playbook (introducing a second `random_id.ingestion_shared_secret_v2` or simply pasting a new hex string), so the `random_id` only generates the **initial** value — subsequent rotations are operator-driven.

The value lands in TF state. The state is encrypted at rest in S3, access-restricted via IAM. This is the standard pattern — TF state is the source of truth for TF-generated secrets. Rotation is `terraform apply -replace=random_id.ingestion_shared_secret` followed by the C-1 two-secret dance (§13.2).

## 9. Edge (dashboard hosting)

### 9.1 Option A — App Runner serving the dashboard (rejected)

The compose stack today runs the dashboard as an nginx container (`services/dashboard/Dockerfile`, `services/dashboard/nginx.conf`) that serves the built SPA from `/usr/share/nginx/html`, proxies `/api/*` to the api container, and runs `inject-env.sh` at startup to populate `/runtime-env.js`. This shape ports to App Runner by:

- Pushing the dashboard image to ECR.
- A third App Runner service `axiaops-dashboard` on port 80.
- Wiring api on the same App Runner VPC connector so the nginx `proxy_pass` reaches it.

Cost: +€5-€10/mo for a third always-warm service (the dashboard is the entry point for every browser session, so it doesn't scale to zero like ingestion does). Plus the nginx container is doing nothing CloudFront can't do natively (path-routing, security headers, gzip).

### 9.2 Option B — CloudFront + S3 (recommended)

Skip the nginx container entirely. Build the SPA in CI, sync the `dist/` directory to an S3 bucket, point CloudFront at the bucket as one origin and at App Runner api as a second origin. Path-based behaviour routes:

- `/api/*` and `/v1/*` → App Runner api origin (strip the `/api` prefix via a Function or CloudFront rewrite — see §9.4).
- everything else → S3 origin, fallback to `/index.html` for SPA client-side routing.

CloudFront pricing: €0.085/GB out for the first 10 TB (cheaper for EU origins), €0.01/10k requests. AxiaOps's traffic — a handful of operators, an SPA bundle of ~2MB compressed, occasional dashboard reloads — sits firmly in "<€2/mo" territory. The S3 bucket itself is cents per month.

CloudFront also handles security headers (`Strict-Transport-Security`, `X-Frame-Options`, `Content-Security-Policy`) via a CloudFront Response Headers Policy — replacing the per-location `add_header` repetition in `services/dashboard/nginx.conf:38-76` with a single declarative policy.

**Decision: Option B.**

### 9.3 The `runtime-env.js` problem

The compose-mode `inject-env.sh` writes `window.__ENV__ = {...}` into `runtime-env.js` at container startup, populated from env vars (DEV_MODE, DEV_ORG_NAME, FEATURE_ROLE_AUTH, AXIAOPS_AWS_ACCOUNT_ID). CloudFront + S3 doesn't run scripts at deploy time — the file in S3 is the file the browser gets.

Three resolution options:

- **A. Compute `runtime-env.js` in the CI dashboard build job** before syncing to S3. The CI job reads the deploy-time env vars (which it has — they're CI variables) and writes a static `runtime-env.js` into `dist/`, then syncs. Per-env values land at build time, not at container start.
- **B. Use a CloudFront Function** (1ms-budget JS at the edge) to inject env values into HTML responses. Overkill — adds a runtime moving part for a one-time-per-deploy substitution.
- **C. Bake values into the bundle as Vite env vars** at build time. Vite already supports `VITE_*` env vars compiled in at `vite build`. Existing `runtime-env.js` exists precisely so the bundle is env-agnostic (build once, deploy many envs). Production has exactly one env we deploy to (this prod), so the Vite-env shape is fine here.

**Recommendation: A.** It preserves the existing build-once shape (the bundle from CI is what every env gets), but the `runtime-env.js` write is a deploy-time concern done in the deploy job, not at container start. Pseudocode for the deploy script:

```bash
cd services/dashboard/dist
cat > runtime-env.js <<EOF
window.__ENV__ = {
  "DEV_MODE": "false",
  "DEV_ORG_NAME": "",
  "FEATURE_ROLE_AUTH": "${FEATURE_ROLE_AUTH:-false}",
  "AXIAOPS_AWS_ACCOUNT_ID": "${AXIAOPS_AWS_ACCOUNT_ID:-}"
};
EOF
aws s3 sync . s3://axiaops-dashboard-prod/ --delete --cache-control "public, max-age=31536000, immutable" --exclude "*.html" --exclude "runtime-env.js"
aws s3 cp index.html s3://axiaops-dashboard-prod/index.html --cache-control "no-store"
aws s3 cp runtime-env.js s3://axiaops-dashboard-prod/runtime-env.js --cache-control "no-store"
aws cloudfront create-invalidation --distribution-id ${CF_DIST_ID} --paths "/index.html" "/runtime-env.js"
```

The `/assets/*` files (Vite fingerprinted) get long-lived immutable caching; `index.html` and `runtime-env.js` get `no-store` (per the same logic the nginx config encodes for the un-fingerprinted files). CloudFront invalidation runs on those two paths only.

### 9.4 CloudFront origin routing

Two origins:

```hcl
origin {
  domain_name = aws_s3_bucket.dashboard.bucket_regional_domain_name
  origin_id   = "S3-spa"
  origin_access_control_id = aws_cloudfront_origin_access_control.s3.id
}

origin {
  domain_name = replace(aws_apprunner_service.api.service_url, "https://", "")
  origin_id   = "AppRunner-api"
  custom_origin_config {
    http_port              = 80
    https_port             = 443
    origin_protocol_policy = "https-only"
    origin_ssl_protocols   = ["TLSv1.2"]
  }
}
```

Two cache behaviours:

- Default behaviour (path `*`) → `S3-spa`. SPA fallback to `index.html` via a CloudFront Function (`event.request.uri = '/index.html'` when the path has no extension and isn't `/assets/...`). Long cache on `/assets/*`, no-store on `/index.html` and `/runtime-env.js` (controlled by S3 object metadata, see §9.3).

- Behaviour for path patterns `api/*` and `v1/*` → `AppRunner-api`. CloudFront Function strips the `/api/` prefix before forwarding. **No caching** (TTL 0). Forward all query strings, all cookies (the session cookie), the `Authorization` header.

**Why a CloudFront Function rather than letting the api see `/api/v1/zombies` paths.** The api today (and the nginx proxy config) expects to receive `/v1/zombies` — the `/api/` prefix is the SPA's convention to disambiguate from SPA routes. The Function strips the prefix so the api code stays unchanged:

```javascript
function handler(event) {
  const r = event.request;
  if (r.uri.startsWith('/api/')) {
    r.uri = r.uri.substring(4);  // drop '/api'
  }
  return r;
}
```

**Block `/api/metrics`** at CloudFront — `services/dashboard/nginx.conf:99-101` returns 404 for `/api/metrics`, blocking external `/metrics` scrapes (which carry customer_id and licence telemetry as Prometheus labels per `docs/license-issuance.md` §"Scraping `/metrics` (internal only)"). Port this guard to CloudFront via a Function:

```javascript
function handler(event) {
  const r = event.request;
  if (r.uri === '/api/metrics' || r.uri === '/v1/metrics') {
    return { statusCode: 404, statusDescription: 'Not Found' };
  }
  if (r.uri.startsWith('/api/')) {
    r.uri = r.uri.substring(4);
  }
  return r;
}
```

### 9.5 ACM cert in us-east-1

CloudFront requires its viewer cert to live in `us-east-1` (a long-standing CloudFront limitation). The cert covers `app.axiaops.io` and optionally `www.app.axiaops.io`. DNS-01 validation via Route 53 — the cert resource creates the validation CNAMEs in the hosted zone.

This requires a second AWS provider alias in `infra/terraform/modules/edge/providers.tf`:

```hcl
provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"
}

resource "aws_acm_certificate" "cloudfront" {
  provider          = aws.us_east_1
  domain_name       = "app.axiaops.io"
  validation_method = "DNS"
  lifecycle {
    create_before_destroy = true
  }
}
```

The Route 53 zone itself lives in `eu-central-1` (Route 53 is global; the region attribute is just an API endpoint preference).

2. Operator logs into the registrar, sets the domain's NS to the Route 53 NS records.
3. Wait 24h-48h for DNS propagation. (The first apply will succeed; only the ACM validation will hang until propagation completes. ACM auto-retries.)

## 10. IAM

### 10.1 GitLab CI deploy role

The current setup (`docs/CI_CD_SECRETS_SETUP.md`) uses an IAM **user** with long-lived access keys stored as GitLab CI variables. **We're replacing this with OIDC federation.** GitLab has been a registered OIDC IdP for AWS since 2022; the trust relationship is:

```hcl
resource "aws_iam_openid_connect_provider" "gitlab" {
  url             = "https://gitlab.com"
  client_id_list  = ["https://gitlab.com"]
  thumbprint_list = [data.tls_certificate.gitlab.certificates[0].sha1_fingerprint]
}

data "tls_certificate" "gitlab" {
  url = "https://gitlab.com"
}

resource "aws_iam_role" "gitlab_ci_deploy" {
  name = "gitlab-ci-axiaops-deploy"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = { Federated = aws_iam_openid_connect_provider.gitlab.arn }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "gitlab.com:aud" = "https://gitlab.com"
        }
        StringLike = {
          "gitlab.com:sub" = [
            "project_path:axiaops/axiaops:ref_type:branch:ref:main",
            "project_path:axiaops/axiaops:ref_type:branch:ref:develop",
            "project_path:axiaops/axiaops:ref_type:tag:ref:*",
          ]
        }
      }
    }]
  })
}
```

The trust policy locks the role to:
- Specific project (`axiaops/axiaops`).
- Specific refs: main branch, develop branch, and any tag. Feature/MR branches **cannot** assume this role — they can't deploy to production.

The CI job acquires a short-lived JWT (10-min default) via the **`id_tokens:` job declaration** and exchanges it for AWS credentials via `aws sts assume-role-with-web-identity`. No long-lived access keys.

> **Note on `CI_JOB_JWT_V2`.** GitLab deprecated `CI_JOB_JWT_V2` in mid-2023; jobs that still reference it now receive an empty string and the `sts:AssumeRoleWithWebIdentity` call fails silently. The replacement is the `id_tokens:` YAML block in `.gitlab-ci.yml`:
>
> ```yaml
> deploy:production:
>   id_tokens:
>     AWS_CI_JWT:
>       aud: https://gitlab.com
>   before_script:
>     - >
>       aws sts assume-role-with-web-identity
>       --role-arn $AWS_CI_ROLE_ARN
>       --role-session-name "gitlab-ci-$CI_JOB_ID"
>       --web-identity-token $AWS_CI_JWT
>       --duration-seconds 900
> ```
>
> MR 5 (the CI migration) MUST use `id_tokens:`, not `CI_JOB_JWT_V2`. The GitLab project also needs the OIDC IdP registered in AWS (the `aws_iam_openid_connect_provider.gitlab` resource above) **before** MR 5 lands — otherwise the assume-role call fails with `InvalidIdentityToken`.

**Why this is worth doing in v1:** the current long-lived keys (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` as GitLab CI variables per `docs/CI_CD_SECRETS_SETUP.md` step 1.2) are the single highest-blast-radius secret in the system. A leak gives an attacker permanent push access to ECR and update access to App Runner. OIDC federation collapses the blast radius to 10 minutes per job. The setup cost is ~50 lines of TF.

### 10.4 RDS IAM auth — out of scope

RDS supports IAM database authentication, where the IAM identity gets a short-lived token instead of a Postgres password. That would mean:
- App Runner instance role gets `rds-db:connect` permission.
- The Go pgx pool needs a callback that mints a new token before each connection.
- The `axiaops` Postgres role needs `GRANT rds_iam TO axiaops`.

Benefit: no DB password to rotate. Drawback: ~30-60 lines of Go in the pgx pool initializer, and the `axiaops_owner` user STILL needs a password (RDS IAM auth doesn't support master users) so we'd still have one secret in SSM. Net win is small.

**Decision: defer. Continue using Postgres passwords stored in SSM SecureString.** Revisit if SOC 2 type II reviewers specifically call out IAM auth as a requirement.

## 11. Observability

### 11.1 CloudWatch log groups

Two log groups, both 7-day retention per `CLAUDE.md` → "Cost Awareness" mandate:

```hcl
resource "aws_cloudwatch_log_group" "apprunner_api" {
  name              = "/aws/apprunner/axiaops-api/${aws_apprunner_service.api.service_id}/application"
  retention_in_days = 7
}

resource "aws_cloudwatch_log_group" "apprunner_ingestion" {
  name              = "/aws/apprunner/axiaops-ingestion/${aws_apprunner_service.ingestion.service_id}/application"
  retention_in_days = 7
}

resource "aws_cloudwatch_log_group" "ecs_migrate" {
  name              = "/aws/ecs/axiaops-migrate"
  retention_in_days = 7
}
```

App Runner has a convention for log group names (`/aws/apprunner/<service-name>/<service-id>/application` for application logs, `.../service` for service-level events). Pre-creating the log groups via TF prevents App Runner from auto-creating them with the default 30-day retention — without this pre-creation step the retention silently defaults to "never expire" or 30 days depending on the App Runner build, and CloudWatch logs at AxiaOps's log volume can add €5-€10/mo of accumulated cost over months. Pre-creating with 7-day retention is mandatory.

### 11.2 The `/metrics` endpoint is internal

The api and ingestion binaries expose Prometheus metrics on `/metrics` (`services/shared/CLAUDE.md` → "Observability"). The CloudFront Function in §9.4 blocks external scrapes (`/api/metrics` returns 404, matching the nginx config). The metrics endpoints are reachable inside the VPC connector subnet via the App Runner service's private hostname.

**Production Prometheus scraping is OUT OF SCOPE for v1.** Without a scraper, the metrics endpoints exist but no time-series data lands anywhere. This is a known gap and matches the current state of the dev / staging self-hosted envs. The path forward (deferred):

- Run a managed Prometheus (Grafana Cloud free tier — €0/mo for 10k series, which covers AxiaOps) and have a CloudWatch-shipped log of `/metrics` scraping target lists; or
- Run a small Prometheus container on Fargate scraping the App Runner private URLs (~€8/mo) writing to a managed remote_write target.

Either approach is a follow-up MR with its own design pass. The TF in this MR leaves the metrics endpoints exposed but unscraped.

### 11.3 No CloudWatch alarms in v1

No `aws_cloudwatch_metric_alarm` resources. The metrics that would fire (license_days_remaining, hmac_failures_total) come from the application's Prometheus endpoint, which isn't scraped to CloudWatch in v1. CloudWatch's own RDS metrics (CPU, free storage, connections) would alarm-fire usefully, but without a paging seam — email-from-SNS-to-PagerDuty, etc. — alarms without escalation are noise. **Add alarms in the same MR that adds the paging seam.**

The minimum we should do in v1 is to set the RDS billing alarm (account-wide, not per-resource) at €40/mo to catch a runaway-cost incident. That belongs in the AWS Billing console, not TF — billing alarms are global and managed out-of-band.

## 13. Bootstrap and operational playbook

### 13.1 First-apply sequence

Run these in order. Each step is a separate `terraform apply` because the dependencies cross module boundaries in ways the operator should be able to inspect plan output for, mid-sequence.

```
1. infra/terraform/bootstrap        → S3 state bucket + DynamoDB lock + state-readonly role (§4.2)
2. infra/terraform/environments/production with -target=module.network
                                    → VPC, subnets, IGW, security groups, VPC connector
3. infra/terraform/environments/production with -target=module.secrets
                                    → SSM parameters with placeholder values
4. Operator: out-of-band populate AXIAOPS_LICENSE in SSM (§8.4) — `aws ssm put-parameter`
5. infra/terraform/environments/production with -target=module.data
                                    → RDS instance (uses owner password from secrets)
                                    → ~10-minute apply due to RDS provisioning
6. infra/terraform/environments/production with -target=module.iam
                                    → GitLab OIDC provider + role
                                    → App Runner instance roles
                                    → Migrate task roles
7. infra/terraform/environments/production with -target=module.compute
                                    → ECR repos
                                    → ECS task definition for migrate
                                    → App Runner services (api + ingestion)
                                    → API services start, fail health check (no app user yet)
8. Operator: push first images to ECR (manual `docker push` on the operator's machine, since
   the CI deploy role exists but the CI pipeline hasn't been migrated yet)
9. Operator: run the migrate task once (creates the `axiaops` app user + schema)
   aws ecs run-task --task-definition axiaops-migrate --cluster axiaops-migrate --launch-type FARGATE \
     --network-configuration "awsvpcConfiguration={subnets=[...],securityGroups=[...]}"
10. App Runner services pick up working DATABASE_URL on next deploy
    aws apprunner start-deployment --service-arn <api-arn>
    aws apprunner start-deployment --service-arn <ingestion-arn>
11. infra/terraform/environments/production with -target=module.edge
                                    → S3 bucket, ACM cert, CloudFront distribution, Route 53 records
                                    → ACM validation hangs until step 12
12. Operator: at the domain registrar, point axiaops.io NS records at the Route 53 NS values
13. Wait ~30-60 minutes for ACM validation
14. infra/terraform/environments/production (no -target)
                                    → final no-diff apply, sanity check
15. Operator: build and push the dashboard bundle (manual `aws s3 sync` first time);
    test https://app.axiaops.io loads.
16. Operator: install the GitLab CI deploy role in GitLab CI variables; update .gitlab-ci.yml

```

The `-target=` pattern is deliberately operator-driven for the first apply. Subsequent applies (`terraform apply` with no target) should produce a no-op plan once everything is in place.

### 13.2 Rotating the C-1 HMAC secret without downtime

Follows the playbook in `docs/c1-hmac-plan.md` §5, translated to TF actions. Uses the three-variable split from §8.3.

```
Pre-state: api_ingestion_secret = X
           ingestion_primary_secret = X
           ingestion_next_secret = X  (defensive duplicate)
           All three SSM parameters carry X. Both binaries running with X loaded.

Step 1 — Stage new secret Y on ingestion's _NEXT slot.
  • Edit infra/terraform/environments/production/main.tf:
      module "secrets" {
        api_ingestion_secret     = "X"   # unchanged
        ingestion_primary_secret = "X"   # unchanged
        ingestion_next_secret    = "Y"   # ← new value
      }
  • terraform apply
      → updates /axiaops/prod/ingestion/INGESTION_SHARED_SECRET_NEXT to Y
      → /axiaops/prod/api/INGESTION_SHARED_SECRET still X
      → /axiaops/prod/ingestion/INGESTION_SHARED_SECRET still X
  • Trigger ingestion redeploy via CI button (or aws apprunner start-deployment)
  • Ingestion process reloads: primary=X, next=Y. Accepts X AND Y.
  • API process still has X. Still signs with X. Ingestion happy.

Step 2 — Flip api signer to Y. Ingestion primary stays X.
  • Edit infra/terraform/environments/production/main.tf:
      module "secrets" {
        api_ingestion_secret     = "Y"   # ← flipped
        ingestion_primary_secret = "X"   # unchanged — KEEP X HERE
        ingestion_next_secret    = "Y"   # unchanged
      }
  • terraform apply
      → updates /axiaops/prod/api/INGESTION_SHARED_SECRET to Y
      → ingestion's SSM both unchanged
  • Trigger api redeploy (only api needs to redeploy; ingestion still accepts both X and Y)
  • API process reloads: signs with Y.
  • Ingestion has primary=X next=Y loaded — accepts Y. Happy.

Step 3 — Promote Y to ingestion primary, clear _NEXT.
  • Edit infra/terraform/environments/production/main.tf:
      module "secrets" {
        api_ingestion_secret     = "Y"   # unchanged
        ingestion_primary_secret = "Y"   # ← promoted
        ingestion_next_secret    = "Y"   # defensive — same value as primary (steady-state shape)
      }
  • terraform apply
      → updates /axiaops/prod/ingestion/INGESTION_SHARED_SECRET to Y
      → /axiaops/prod/ingestion/INGESTION_SHARED_SECRET_NEXT stays Y
  • Trigger ingestion redeploy
  • Ingestion process reloads: primary=Y, next=Y. Accepts Y only. Rejects X.
  • API still signs with Y. Happy.

Post-state: all three values = Y. Same steady-state shape as pre-state, with Y instead of X.
```

The three apply windows are designed around the live-process state, not just the SSM state. At every point, the api's signing key matches at least one of ingestion's loaded keys. Three separate `terraform apply` runs with a redeploy between each are non-negotiable — combining steps would create a window where api signs with Y while ingestion's loaded process only knows X.

If the TF state stores the new secret values, anyone with state-read access learns the secret. Standard caveat — state is encrypted at rest + access-restricted.

### 13.3 Rolling back an App Runner service to a prior image

The ECR lifecycle keeps the last 30 tagged images. To roll back the api to the image from yesterday:

```bash
# Find the previous tag
aws ecr describe-images --repository-name axiaops-api \
  --query 'sort_by(imageDetails,& imagePushedAt)[*].[imagePushedAt,imageTags[0]]' \
  --output table

# Roll back
aws apprunner update-service \
  --service-arn arn:aws:apprunner:eu-central-1:123456789012:service/axiaops-api/<service-id> \
  --source-configuration "ImageRepository={ImageIdentifier=123456789012.dkr.ecr.eu-central-1.amazonaws.com/axiaops-api:main-abc1234,ImageRepositoryType=ECR,ImageConfiguration={Port=8080}}"
```

The rollback typically completes in 2-5 minutes (App Runner pulls the image, starts a new instance, switches traffic, terminates the old instance). No TF involved — TF's `ignore_changes = [image_identifier]` keeps the rollback out of state drift.

For coordinated rollbacks (api + ingestion together), run both `apprunner update-service` calls in quick succession; App Runner doesn't serialize them.

### 13.4 RDS disaster recovery

**Restore-from-snapshot** (full DR; assume the live RDS is unrecoverable):

```bash
# 1. List recent snapshots
aws rds describe-db-snapshots --db-instance-identifier axiaops-prod \
  --query 'DBSnapshots[*].[DBSnapshotIdentifier,SnapshotCreateTime,Status]' \
  --output table

# 2. Restore to a new instance
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier axiaops-prod-restore \
  --db-snapshot-identifier rds:axiaops-prod-2026-05-17-02-30 \
  --db-subnet-group-name axiaops-prod-subnet-group \
  --vpc-security-group-ids sg-<rds_sg_id> \
  --no-publicly-accessible \
  --db-instance-class db.t4g.micro

# 3. Wait ~10-15 min for available state
aws rds wait db-instance-available --db-instance-identifier axiaops-prod-restore

# 4. Update SSM parameters to point at the new endpoint
aws ssm put-parameter --name /axiaops/prod/api/DATABASE_URL --overwrite \
  --value "postgres://axiaops:<pw>@axiaops-prod-restore.<id>.eu-central-1.rds.amazonaws.com:5432/axiaops?sslmode=require"
# (repeat for ingestion + migrate)

# 5. Redeploy App Runner services to pick up new DATABASE_URL
aws apprunner start-deployment --service-arn <api-arn>
aws apprunner start-deployment --service-arn <ingestion-arn>

# 6. Validate dashboard loads, recent zombies present.

# 7. Once stable, delete the old RDS instance (skip-final-snapshot if it's truly gone)
#    OR rename the restored instance to the canonical name:
aws rds modify-db-instance --db-instance-identifier axiaops-prod-restore \
  --new-db-instance-identifier axiaops-prod --apply-immediately
```

The rename takes another ~5-10 min and incurs a second endpoint change — repeat the SSM update + redeploy. The TF state will show drift on the RDS `identifier` attribute; `terraform import` to rebind, or accept the drift until the next planned change.

**Point-in-time recovery to a specific second** within the 7-day window:

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier axiaops-prod \
  --target-db-instance-identifier axiaops-prod-pitr \
  --restore-time 2026-05-17T14:30:00Z \
  --db-subnet-group-name axiaops-prod-subnet-group \
  --vpc-security-group-ids sg-<rds_sg_id>
```

Same procedure from step 3 onwards.

### 13.5 App Runner re-create from image tag

Not all incidents involve RDS. If an App Runner service is genuinely lost (rare; AWS-side issue), TF can re-create it from the same image tag:

```bash
# TF state still has the service resource; apply re-creates with the same config
cd infra/terraform/environments/production
terraform apply -target=module.compute.aws_apprunner_service.api
```

The new service comes up with the **default image identifier** (`:latest`), which may be ahead of or behind the desired state depending on the last successful CI deploy. After re-create, run the CI deploy job to land the intended image.

### 13.6 Rotating the AxiaOps license JWT

The license is valid for 365 days. Operator-managed renewal:

1. ~45 days before expiry, the Prometheus alert `axiaops_license_days_remaining < 30` should fire (when the scraping seam is in place; for now, an operator calendar reminder).
2. Operator mints a new JWT (`docs/license-issuance.md` → "Issuing a license for a customer", substituting `axiaops-internal-prod`).
3. `aws ssm put-parameter --name /axiaops/prod/api/AXIAOPS_LICENSE --overwrite --value "$(cat new.jwt)"`. Same for ingestion's path.
4. Trigger redeploy of both services. The new JWT is in effect after redeploy.

The TF `aws_ssm_parameter` resource for `AXIAOPS_LICENSE` has `lifecycle.ignore_changes = [value]` precisely so the out-of-band rotation doesn't trigger TF drift.

| RDS IAM auth | **Defer** | See §10.4. SSM-stored passwords are the simpler path; IAM auth doesn't eliminate the owner-password secret. |
| App Runner private services for ingestion | **Defer** | See §2.2 path A/B. Public hop with HMAC is the v1 default; revisit once C-1 lands and logs show ingestion's public surface is signature-rejecting all unexpected traffic. |
| ElastiCache for Redis | **No** | Redis usage (JWKS cache, rate limiter, queue) per `services/shared/CLAUDE.md` is optional — the codebase has in-memory fallbacks (`cache.New(redisURL)` selects backend on `REDIS_URL` presence). ElastiCache Serverless minimum is €40+/mo, which alone blows the €24-34 budget. Run without Redis in prod v1; revisit when a feature genuinely demands it. |
| EventBridge cron for scheduled scans | **No** | The in-process ticker in api already does this per `account.scan_interval_hours`. EventBridge is a feature, not a fix. |
| KMS customer-managed keys for SSM/S3/RDS | **No** | Each costs €1/mo and adds auditable key-usage events. Defer until SOC 2 type II reviewer calls it out as a finding. |
| AWS Backup for cross-region backup | **No** | RDS automated backups are in-region; AWS Backup for cross-region replication is €0.095/GB-month plus transfer. Single-region DR via snapshots is sufficient. |
| Observability target — Grafana Cloud vs CloudWatch | **Decide before alerting** | The current MR doesn't wire alerting; the next MR that adds Prometheus scraping picks one. Recommend Grafana Cloud free tier (10k series) as the v1 target. |
| Multi-tenant SaaS data plane | **Out of scope per ADR-0001** | Self-hosted-first means AxiaOps prod hosts AxiaOps. The SaaS posture is deferred indefinitely. |

## 15. Sequencing

### 15.1 What to land first

**MR 1 — TF state backend + ECR repos.** Self-contained, low blast radius. Provisions S3 + DynamoDB + ECR but does NOT touch any compute or data. After this MR, the CI pipeline can push images to the new ECR repos without rest of the infra in place.

- Files: `infra/terraform/bootstrap/*`, `infra/terraform/environments/production/{providers.tf,main.tf}` with only the `network` (VPC outputs) and `compute` (ECR-only) modules referenced.
- Effort: ~1-2 days.
- Validation: `terraform apply` succeeds. `docker push` to one of the ECR repos succeeds from operator's laptop.

**MR 2 — Network + Data + IAM core.** Provisions the VPC, RDS, GitLab OIDC role, App Runner instance roles. Does NOT provision App Runner services yet.

- Files: `infra/terraform/modules/{network,data,iam}/*`, expand `environments/production/main.tf`.
- Effort: ~3-4 days, mostly RDS + IAM trust-policy tuning.
- Validation: RDS reachable from a one-off Fargate task. GitLab CI can assume the deploy role.

**MR 3 — Secrets + Compute (App Runner services + migrate task).** Provisions SSM parameters, ECS migrate task definition, App Runner api and ingestion services.

- Files: `infra/terraform/modules/{secrets,compute,observability}/*`.
- Effort: ~4-5 days.
- Validation: App Runner services come up; migrate task creates the `axiaops` user and runs all migrations; api `/livez` returns 200.

**MR 4 — Edge (dashboard hosting).** Provisions S3, CloudFront, ACM cert, Route 53.

- Files: `infra/terraform/modules/edge/*`.
- Effort: ~3-4 days, with ~24-48h waiting for DNS propagation interspersed.
- Validation: `https://app.axiaops.io` loads, end-to-end browser → CloudFront → api → RDS works.

**MR 5 — CI migration to OIDC role.** Updates `.gitlab-ci.yml` to assume the new role instead of using long-lived keys. Removes `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` from GitLab CI variables.

- Files: `.gitlab-ci.yml`, `docs/CI_CD_SECRETS_SETUP.md` (rewrite for the OIDC posture).
- Effort: ~1-2 days.
- Validation: A test deploy from a `main`-branch pipeline succeeds.

**MR 6 — `docs/ops.md` runbook.** Captures the operational playbook from §13 in a dedicated runbook, with the field-tested commands operators actually need.

- Files: `docs/ops.md`.
- Effort: ~1 day.

### 15.2 Estimated total effort

- 6 MRs.
- ~13-17 working days of focused work.
- Strung over ~3-4 weeks calendar time (DNS propagation, RDS provisioning, code review gaps).
- Plus ~3-5 days of unanticipated AWS-quirk debugging — budget it.

### 15.3 What NOT to do in MR 1

Avoid the temptation to "just include the App Runner service so we can see it working." Each MR should be reviewable in isolation and reversible without breaking the next. Compute depends on network + data + secrets; ship them in order.

**Expected partial-CI state during the rollout.** Between MR 1 (ECR repos exist) and MR 3 (App Runner services exist), the CI `deploy:production` job will succeed for its `docker push` steps and fail when it calls `apprunner update-service` (the service doesn't exist yet). This is expected, not a regression — the operator should leave `deploy:production` un-clicked during this ~2-week window. Document this prominently in the MR 1 description so future-self doesn't chase it as a deploy bug.

### 15.4 Pre-merge gates

For each MR:

- `terraform fmt -check` clean.
- `terraform validate` clean.
- `terraform plan` output in the MR description (or a CI job that posts it as an MR comment).
- For MR 2-4: a smoke check (e.g., RDS reachable, App Runner returns 200, etc.) recorded in the MR description.
- One code review from someone outside the author (the code-reviewer agent, then a human if it's a substantive change).

After MR 5 lands, the CI deploy job's `aws apprunner update-service` calls (currently using `AWS_ACCESS_KEY_ID` per `docs/CI_CD_SECRETS_SETUP.md`) start using the OIDC-federated role. Decommission the IAM user `gitlab-ci-axiaops` and rotate any other credentials it touched.
